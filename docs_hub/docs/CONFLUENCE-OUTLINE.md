## 작업 방식

- **한 번에 다 하지 않고 페이지 단위로 하나씩** 진행한다(여러 세션에 걸쳐).
- 각 페이지 작성 시점에 **그 페이지에 필요한 다이어그램(토폴로지/시퀀스/상태도/ERD 등)을 그 자리에서 함께 그린다.** 다이어그램은 Confluence Mermaid/PlantUML로 작성.
- 본문 원본은 `docs/ref/*` 와 소스코드. 작성 전 해당 원본을 코드와 대조(문서-구현 일치 확인은 2026-06-06 1차 완료).

### 설계 단계 흐름 (2026-06-11 정리)

문서는 **설계 단계 = 요구사항 → 아키텍처 → 시나리오 → 시퀀스 다이어그램** 순으로 읽히도록 구성한다(2·3·4장). 그 뒤 5장 **상세 구현**이 "어떻게 만들었나"를 4단 템플릿으로 받친다.

> 단, 본 프로젝트의 시나리오·시퀀스는 사전 설계 산출물이 아니라 **이미 구현·검증된 시스템을 반영한 동작 흐름**이다(reverse-documentation). 그래서 추정이 아니라 실제 코드(토픽/서비스/FSM)와 1:1로 일치한다 — 각 시퀀스 페이지 머리말에 "실제 구현 반영"임을 명시.

## 상세구현(5장) 작성 템플릿 — 4단 구성

모든 `5.x` 페이지는 동일한 4단으로 작성한다(일관성 + 면접 설명 최적화):

1. **왜 개발했나** — 요구·문제 정의 + **그 기술/설계를 택한 의사결정 근거(왜 이걸 선택했나)**
2. **어떻게 개발했나** — 설계·구현 상세
3. **문제 상황과 해결** — 개발 중 마주친 문제와 트러블슈팅(이런 문제가 있어 이렇게 해결)
4. **결과·파라미터** — 검증값·확정 파라미터

> 의사결정 기록(왜)·트러블슈팅(문제해결)은 별도 섹션을 두지 않고 **각 상세문서의 ①·③에 통합**한다.

## 시나리오 ↔ 시퀀스 매핑 (4.2 ↔ 4.3) — 2026-06-11 확정 (7종)

시나리오(글)와 시퀀스(그림)는 1:1로 묶어 같은 흐름을 글+그림 한 쌍으로 설명한다.
**정상 흐름(S1~S3) = 성공적 임무 수행의 시간 순 단계 / 예외 흐름(S4~S7) = 그 수행 도중 끼어드는 예외·개입.**

| 구분 | 시나리오(4.2, 서술) | 시퀀스(4.3, 그림) |
|---|---|---|
| 정상 | S1 임무 요청 — 예약/현장방문(walk-in) alt + 만차·대기 분기 | ① 임무 요청 |
| 정상 | S2 임무 배정 & 출발 — dispatcher 폴링 → GuideGoal → 출발멘트 발화 후 출발(DEC-048) | ② 임무 배정 & 출발 |
| 정상 | S3 안내 주행 → 도착 TTS → 복귀 → 홈 도킹 → IDLE (임무 사이클 전체) | ③ 임무 사이클 |
| 예외 | S4 안내 중 사람 감지 정지/재개 | ④ 사람 감지 |
| 예외 | S5 멀티로봇 동시운행 충돌회피 | ⑤ pause/resume |
| 예외 | S6 안내 실패 → 관리자 복구 (DEC-044) | ⑥ 실패→복구 |
| 예외 | S7 관리자 긴급 제어 (pause/resume/abort) | ⑦ 긴급 제어 |

> ③에서 도킹은 `/aruco_home_dock` 서비스 요청→성공 응답 한 줄로만 표현(시나리오 수준). **PBVS 3단계 내부 동작 상세 시퀀스는 5.7 페이지**에 둔다(기존 ④ 도킹 초안 이동).
